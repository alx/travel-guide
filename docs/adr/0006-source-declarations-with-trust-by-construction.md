# News source declarations with trust-by-construction

The GPS Newsletter pipeline started with a flat, scalar `feeds` block on each GeoJSON feature: `company_rss`, `company_url`, `changedetection_url`, `keywords`, `sector_rss`. That shape worked at 5 source types and 69 features. Scaling to ~10 source types per company — to close the 61/69 gap of companies with no `company_rss` and densify the news signal feeding the AI relevance/classify pipeline — breaks that shape in four directions at once. This ADR resolves the four directions together because they are not independent: changing any one in isolation creates inconsistencies with the others.

## What changes

**1. The `feeds` block becomes a typed source list.**
Each project feature now carries `feeds.sources: [{type, url, …}]`. `type` is an open enum drawn from the **News source catalog** (`company_rss`, `sector_rss`, `changedetection`, `linkedin_company_rss`, `youtube_channel_rss`, `google_news_query_rss`, `bodacc_rss`, …). `fetch_digest.py` dispatches per `type` against a single dispatch table. Adding a new source type is a one-line dispatch addition plus rows in the data — never a schema migration.

**2. Source declarations split across two stores.**
The declarative half — *what we monitor* — stays in the GeoJSON (and in `companies.json`, see point 3). The operational half — *how the monitor is doing* — moves to a SQLite `news_sources` table of shape `(company_id, type, url, uuid, enabled, added_at, last_fetched_at, last_error)`. The existing `changedetection_uuid` and `rss_uuid` fields on each feature were operational state pretending to be config; they migrate to SQLite. The fetch pipeline reads declarations on startup, upserts into `news_sources` (minting a changedetection.io UUID on first sight where the type calls for it), then iterates the SQLite table to fetch.

**3. Company is promoted to a first-class entity in a sibling JSON file.**
The previous claim in `CONTEXT.md` that "project and company are used interchangeably" was untrue in the data: Eclairion has 3 features, Verso Energy 4, Derichebourg 2, Naval Group 2. Company-level sources (`company_rss`, `linkedin_company_rss`, `youtube_channel_rss`, `bodacc_rss`, `wikipedia_atom`) live in `static/france-grands-projets-strategiques/companies.json`, keyed by **Company slug**. Each project feature carries `properties.company_id` referencing the slug. Project-level sources (`changedetection`, `regional_press_rss`, `boamp_rss` keyed by SIRET, `regulatory_filing` for that site) stay on the feature. The same `company_id` is the foreign key into the SQLite `company_enrichment` table — one identity across all stores.

**4. Trust-by-construction: declarations are verified at write time, not at read time.**
Anything inside `companies.json` or `feeds.sources` is fetched on the next pipeline run with no further gate. Auto-discovery scripts (a new `discover_sources.py --type {...}`, plus the existing `enrich_web.py`) never write to those files directly. They write candidates to a `pending_sources` SQLite table; a Telegram review interface (mirroring the **Finance review interface** pattern) presents each candidate with a preview and Approve / Reject buttons. Approval writes the declaration into the appropriate file as a git-tracked edit. This is retroactive: the precision backlog already in `company_profiles_to_review.md` — Crystalrod matched to a TikTok product page, Arcelor Mittal to an actu.fr article, etc. — gets imported into `pending_sources` and worked through the same queue. `enrich_web.py`'s profile mode is reworked so its output goes to the queue, not directly to `company_enrichment`.

## Considered options

- **Keep scalar fields, just add more named scalars** (`linkedin_rss`, `youtube_rss`, …) — lowest immediate refactor, but every new source type means a schema migration across all 69 features and a new branch in the fetcher; multiple feeds of the same type per project become impossible. Rejected: the explicit goal is fan-out from 5 to ~10 types, and the next round of fan-out will be just as painful.
- **Move everything (declarations + state) to SQLite, drop `feeds` from the GeoJSON** — clean operationally, but a source addition becomes a `sqlite3` write with no PR-reviewable trail. The precision backlog exists *because* `company_enrichment` writes had no audit gate. Rejected: removing the git-diff audit is the wrong direction given the failure mode we already have.
- **Keep declarations in the GeoJSON, including operational fields like `changedetection_uuid`** (status quo, extended) — every fetch run rewrites UUIDs into git, every `last_fetched_at` would land in a commit. Rejected: noise drowns the audit trail and forces either a noisy commit-per-run or pretending state doesn't exist.
- **Denormalize company-level sources across the multiple features of multi-project companies** — keeps everything in the GeoJSON, no sibling file. Rejected: Eclairion's 3 features means a LinkedIn URL fix is 3 edits to keep in sync; the precision backlog proves "one place to fix it" is the constraint, not "one file to read".
- **Auto-write discovered sources directly, flag them with a `confidence: auto` field** — fastest, matches what `enrich_web.py` does today. Rejected for the same reason as the SQLite-only option: pollutes the declarative store with operational metadata and replicates the exact pattern that produced the existing backlog.
- **Pure manual curation, no auto-discovery to a queue** — highest precision but ignores the 550-ish candidate-URL workload. Rejected: pre-fetched candidates with title/favicon/snippet preview make review ~10× faster than cold curation.

## Consequences

The fetch pipeline gets one schema-stable input shape and one dispatch table; new source types are content additions, not code-and-data migrations. The git history of `companies.json` becomes the audit trail for "what are we monitoring and why" — meaningful diffs, meaningful reverts. The `company_profiles_to_review.md` triage workflow is replaced by the Telegram review queue, so corrections happen in a structured store and never leak into untracked Markdown again. The cost is a one-time migration of 69 features to add `company_id`, the creation of `companies.json` with ~55–60 entries (one per unique company), the move of changedetection/RSS UUIDs to the new SQLite table, the addition of a `pending_sources` table and its Telegram bot handler, and a behavior change in `enrich_web.py`. The `Strategic project` and `Company` terms in `CONTEXT.md` are now accurate; the previous interchangeable-usage claim is retired.
